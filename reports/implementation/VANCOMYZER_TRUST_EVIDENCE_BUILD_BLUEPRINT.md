# Vancomyzer Trust & Evidence Build Blueprint

## Purpose
Translate the refined Trust & Evidence implementation spec into a direct build blueprint for Phase 1 implementation.

## Build objective
Create a Trust & Evidence page that:
- explains how Vancomyzer approaches transparency and interpretability
- makes assumptions, limitations, and review behavior visible
- uses one trust-oriented case and one richer documentation example
- reinforces evidence-aware communication without implying unsupported validation

## Final page section order

### 1. Page introduction
Purpose:
- explain why trust, transparency, and interpretability matter
- frame the page as practical guidance, not marketing

Assets:
- page headline
- short purpose statement
- optional CTA: Review a sample case

Guardrails:
- avoid defensive or overpromotional tone
- avoid implying algorithmic authority
- keep language clinician-readable

---

### 2. Transparency principles
Purpose:
- show the philosophy behind the product’s trust model

Assets:
- visible assumptions highlight
- visible method/model highlight
- visible limitations highlight
- clinician-readable outputs highlight

Cross-link:
- optional link to sample case or FAQ

Guardrails:
- keep trust practical, not abstract
- avoid validation or superiority language

---

### 3. What clinicians should review
Purpose:
- explicitly show responsible review behavior before accepting outputs

Required themes:
- patient variables
- model assumptions
- data sufficiency
- interpretation context

Guardrails:
- reinforce clinician oversight
- avoid suggesting blind reliance on outputs

---

### 4. Example workflow interpretation
Purpose:
- demonstrate trust through a concrete example

Selected asset:
- CASE-003 — Sparse level data

Placement notes:
- short explanation only
- connect the case to uncertainty, assumptions, and cautious interpretation
- CTA: Review a sample case

Guardrails:
- do not add multiple cases
- use this case specifically to illustrate trust-through-transparency

---

### 5. Documentation-ready communication
Purpose:
- show how richer output can support interpretation and communication

Selected asset:
- clinical note style export example

Placement notes:
- short preview only
- explain why fuller documentation can improve clarity and review
- CTA: Review a documentation-ready summary

Guardrails:
- do not use the quick-summary export as the primary example here
- avoid efficiency or ROI claims

---

### 6. Evidence-aware communication
Purpose:
- make claims boundaries explicit

Assets:
- trust/evidence core language
- claims guardrail language

Required themes:
- what the product is designed to support
- what the product does not claim
- why caution matters

Guardrails:
- preserve “designed to support,” “intended to help,” and similar patterns
- avoid validation, superiority, outcome, or ROI language

---

### 7. Final CTA
Purpose:
- give the visitor a trust-building next step

Allowed CTA options:
- Review a sample case
- Review a documentation-ready summary
- Explore the FAQ
- Contact us / Request a workflow evaluation

Preferred emphasis:
- primary CTA: Review a sample case
- secondary CTA: Review a documentation-ready summary

Guardrails:
- keep CTA flow example-first
- do not make direct contact the dominant CTA on this page

## Cross-linking rules
Trust & Evidence must link to:
- sample case
- documentation-ready summary
- FAQ
- Contact / Institutional

Do not link primarily to:
- SEO pages
- comparison pages
- feature pages
- newsletters
- resource hub
- growth assets

## Asset map
- intro and principles -> trust/evidence source documents
- claims language -> validation and claims guardrails
- case block -> CASE-003
- documentation block -> clinical note style export
- CTA family -> locked shared CTA family

## Implementation guardrails
- keep section count fixed
- keep one trust-oriented case only
- keep one richer export example only
- keep all language aligned with claims guardrails
- do not expand this page into a general resource hub
- preserve Phase 1 scope

## Builder note
This blueprint should be sufficient to implement the Trust & Evidence page without inventing new sections or new trust-specific asset variants.
